# LeadForge AI — мастер-промпт для AI-кодера
### Telegram-бот для сбора и структурирования лидов из 2GIS/Instagram/сайтов в Google Sheets

> Рабочее название проекта — **LeadForge AI**. Можно переименовать, в коде и документации ниже используется именно это имя (репозиторий, переменные, таблицы).

---

## 1. PRODUCT OVERVIEW

LeadForge — личный инструмент для ускорения сбора B2B-лидов. Ты находишь компанию в 2GIS/Instagram/Google/на сайте, копируешь всё, что видишь (в любом виде, одним или несколькими сообщениями), кидаешь в Telegram-бота — бот через LLM распознаёт содержимое, раскладывает по полям, показывает карточку для проверки и одним тапом добавляет строку в Google Sheets. Дубли компаний определяются автоматически и либо тихо объединяются, либо бот переспрашивает.

Это не CRM и не мультиарендный SaaS — это личный «скоростной насос» для наполнения таблицы лидов, которая дальше используется для холодных продаж (см. связанные проекты — [[cold-outreach]] и в перспективе [[email-mailer-tool]]). Архитектура должна быть готова к росту (несколько пользователей, обогащение, рассылка), но MVP — однопользовательский и максимально простой.

**Ключевая метрика успеха:** от «нашёл компанию» до «лид в таблице» — не больше 2 тапов после отправки текста.

## 2. USER FLOW

1. Пользователь находит компанию в 2GIS/Instagram/на сайте.
2. Копирует всё, что есть, и отправляет одним или несколькими сообщениями подряд в бота (текст, ссылку, номер — что угодно).
3. Бот копит сообщения в буфер (session) 6–8 секунд после последнего сообщения ИЛИ до нажатия «✅ Готово» / команды `/done`.
4. По истечении окна бот запускает AI-извлечение по накопленному тексту → «🔎 Анализирую…».
5. Бот показывает карточку результата с заполненными полями и явно отмечает пустые/неуверенные поля.
6. Бот параллельно проверяет дубли:
   - Если совпадение уверенное (телефон/сайт/Instagram) — сразу показывает «Похоже, это уже есть: [строка #N] — обновить?» с кнопками.
   - Если совпадение сомнительное — показывает обе карточки рядом и просит решить.
   - Если дублей нет — обычная карточка «Добавить в таблицу?».
7. Пользователь жмёт ✅ Добавить / ✏️ Исправить / ❌ Отмена.
8. При «Исправить» — бот показывает список полей инлайн-кнопками, пользователь выбирает поле и присылает новое значение одним сообщением.
9. После подтверждения — запись в локальную БД → синхронизация строки в Google Sheets → «✅ Лид добавлен, строка #127».
10. В любой момент: `/last` — последние добавленные лиды, `/search` — поиск по имени/телефону/instagram, `/stats` — сколько добавлено и во сколько это обошлось по AI, `/undo` — откатить последнее действие.

## 3. TECH STACK

| Компонент | Выбор | Почему |
|---|---|---|
| Язык | Python 3.11+ | как во всех твоих текущих ботах |
| Telegram-фреймворк | **aiogram 3.x** | тот же стек, что в AI Sales Agent — переиспользуешь опыт, FSM из коробки идеально ложится на сценарий «буферизация → карточка → редактирование» |
| ORM / БД | **SQLAlchemy (async) + SQLite** на старте, с Alembic-миграциями с первого дня | личный инструмент, нагрузка минимальна — Postgres не нужен, но Alembic делает переход на Postgres позже вопросом смены connection-string, а не переписыванием |
| LLM | **OpenRouter** (`google/gemini-2.0-flash-001` по умолчанию, `openai/gpt-4o-mini` как fallback) | тот же LLM-слой, что уже используется в AI Sales Agent — не плодишь новую интеграцию; Gemini Flash дешёвый и хорошо работает с русским/казахским текстом и «грязным» copy-paste из 2GIS |
| Таблица | **Google Sheets API (gspread + google-auth)** | явное требование; сервис-аккаунт, без OAuth-плясок для одного пользователя |
| Валидация/схемы | **Pydantic v2** | строгая JSON-схема для AI-ответа, нормализация телефонов через `phonenumbers` |
| Fuzzy-match | **rapidfuzz** | для дедупликации по названию |
| Деплой | **Docker + Railway**, вебхук через FastAPI-роут (не polling) | тот же паттерн, что у Имплант-Дент / Abramenko Studio — один сервис держит и Telegram-вебхук, и health-check |
| Логи | стандартный `logging` + JSON-форматтер (можно `loguru`, если удобнее агенту) | структурированные логи нужны для отладки AI-пайплайна |

**PostgreSQL с первой версии не нужен.** Личный инструмент, десятки–сотни лидов в день — SQLite с WAL-режимом справится без проблем, а Alembic-миграции с самого начала убирают всю боль будущего переезда.

## 4. ARCHITECTURE

```
Telegram ──▶ aiogram Bot Layer (webhook via FastAPI)
                │
                ▼
        Session Buffer (per-user)
   (копит сообщения 6–8с или до /done)
                │
                ▼
        AI Extraction Service
   (OpenRouter → Pydantic-schema JSON)
                │
                ▼
        Deduplication Service
  (нормализация + поиск кандидатов в SQLite)
                │
        ┌───────┴────────┐
        ▼                ▼
   Review Card UI    Auto-merge (если score ≥ порога)
   (aiogram FSM)
        │
        ▼
   Local DB (SQLite, source of truth)
        │
        ▼
   Google Sheets Sync Service
 (gspread, кэш sheet_row в БД, батч-запись)
```

**Почему локальная БД — источник истины, а не сам Google Sheet.** Поиск дублей, fuzzy-match и блокировки на запись в самой таблице делать неудобно и медленно (это упирается в Sheets API rate limits — 60–100 запросов/мин). SQLite даёт мгновенный локальный поиск, а в Sheets просто зеркалится финальное состояние строки. Если пользователь вручную поправит что-то в самой таблице — это его право, но обратная синхронизация Sheets → бот в MVP не нужна (не запрашивалась и сильно усложняет систему без явной пользы).

**Масштабирование (закладываем сейчас, не реализуем сейчас):**
- В таблице `leads` с первого дня есть поле `owner_user_id` — даже с одним пользователем. Переход на multi-user не потребует миграции схемы.
- Переход SQLite → Postgres: смена `DATABASE_URL`, Alembic прогоняет те же миграции.
- Polling не используется вообще — сразу webhook, так что рост нагрузки не потребует смены транспорта.
- Если объём вырастет (пакетный импорт, обогащение в фоне) — добавляется простая очередь задач (APScheduler для периодики или arq/RQ + Redis для тяжёлых фоновых джобов); в MVP не нужна, весь путь от сообщения до карточки укладывается в секунды.
- Google Sheets API квоты — обходятся локальным кэшем `sheet_row` (не нужно каждый раз искать строку) и батч-записью через `batch_update`.

## 6. GOOGLE SHEETS

Один лист `Leads`, заголовок в первой строке. Порядок колонок фиксирован — бот пишет по индексу колонки, не по названию.

| # | Колонка | Источник |
|---|---|---|
| A | ID | leads.id |
| B | Дата добавления | leads.created_at |
| C | Компания | leads.company_name |
| D | Категория/ниша | leads.category |
| E | Город | leads.city |
| F | Адрес | leads.address |
| G | Телефон | leads.phone |
| H | WhatsApp | leads.whatsapp_number |
| I | Email | leads.email |
| J | Instagram | leads.instagram |
| K | Telegram | leads.telegram |
| L | Сайт | leads.website |
| M | Источник | leads.source |
| N | Ссылка на источник | leads.source_url |
| O | Услуги | leads.services (через запятую) |
| P | Теги/марки | leads.tags |
| Q | Описание | leads.description |
| R | Рейтинг | leads.rating |
| S | Кол-во отзывов | leads.reviews_count |
| T | Контактное лицо | leads.contact_person |
| U | Статус | leads.status |
| V | Приоритет | leads.priority (пусто в MVP) |
| W | Боль клиента | leads.pain_point (пусто в MVP) |
| X | Комментарий | leads.comment |
| Y | Последнее действие | leads.last_action |
| Z | Дата последнего контакта | leads.last_contact_at |
| AA | ⚠️ Требует проверки | leads.needs_review |

Сырой исходный текст в таблицу **не пишем** — он хранится в `raw_messages` в БД и доступен по команде (например, при `/search` или в карточке лида можно дать кнопку «показать исходный текст»). Это держит таблицу читаемой.

**Работа с API:**
- Авторизация — сервис-аккаунт Google, JSON-ключ в переменной окружения (base64), доступ к таблице выдан только на email сервис-аккаунта.
- Добавление строки — `append_row` с уже нормализованными значениями; сразу после записи запоминаем номер строки в `leads.sheet_row`.
- Обновление существующего лида — `update` по кэшированному `sheet_row`, без повторного поиска.
- Защита от гонок — `asyncio.Lock` на уровне сервиса синхронизации (для одного пользователя гонок практически не бывает, но лок защищает от редкого случая параллельной обработки двух сессий).
- Ошибки API (429/5xx) — не блокируем пользователя: лид сохраняется в локальную БД всегда первым, запись в Sheets идёт с ретраями (экспоненциальный backoff, до 5 попыток) в фоне; если все попытки не удались — лид помечается `sheet_row = NULL` и уходит в очередь ручной досинхронизации (простая команда `/resync`, можно добавить в MVP как safety-net).

## 7. AI EXTRACTION

### Принципы
- AI **не выдумывает** отсутствующие данные — только то, что явно есть в тексте.
- Если поле не определяется — `null`, а не пустая строка и не «домысел».
- Всё, в чём модель не уверена, попадает в `uncertain_fields` — на это карточка обзора ставит ⚠️.
- Телефоны нормализуются в E.164 (`phonenumbers`, дефолтный регион KZ), исходное написание сохраняется отдельно для аудита.
- Ссылки очищаются от трекинговых параметров (utm_*, fbclid и т.п.), схема и `www.` приводятся к единому виду.
- Instagram/Telegram — сохраняется чистый username без `@` и без домена.

### JSON Schema (передаётся модели как контракт ответа)

```json
{
  "company_name": "string | null",
  "category": "string | null",
  "city": "string | null",
  "address": "string | null",
  "phone_raw": "string | null",
  "phone_e164": "string | null",
  "has_whatsapp": "boolean | null",
  "whatsapp_number": "string | null",
  "email": "string | null",
  "instagram": "string | null",
  "telegram": "string | null",
  "website": "string | null",
  "services": ["string"],
  "tags": ["string"],
  "description": "string | null",
  "rating": "number | null",
  "reviews_count": "integer | null",
  "contact_person": "string | null",
  "source_guess": "2gis | instagram | website | google | other | null",
  "source_url": "string | null",
  "uncertain_fields": ["string"],
  "extraction_notes": "string | null"
}
```

Промпт модели фиксирует роль («ты извлекаешь факты, не сочиняешь»), даёт схему, один-два примера (в т.ч. пример «мусорного» ввода → почти все поля `null`), и требует **строго** валидный JSON без markdown-обёртки. Ответ парсится через Pydantic-модель — при ошибке валидации делается один retry с уточняющим замечанием об ошибке, затем fallback на вторую модель.

### Стоимость AI-запросов

Один запрос на извлечение: ~400–600 токенов на промпт+схему, ~200–500 токенов на входной текст лида, ~150–250 токенов на ответ → 800–1400 токенов суммарно. На `gemini-2.0-flash-001` это доли цента (счётчик ведётся в `extraction_logs.cost_usd_est`). При 50 лидах/день расход — не больше пары долларов в месяц, `/stats` показывает накопленную сумму за период. Повторного вызова AI при ручном редактировании поля не происходит — это прямой апдейт в БД, не новое извлечение.

## 8. DEDUPLICATION

### Нормализация перед сравнением
- Телефон → E.164, сравнение по последним 9–10 цифрам (на случай разного кода страны/форматирования).
- Сайт → без протокола, без `www.`, без query-параметров, без trailing slash.
- Instagram/Telegram → lowercase, без `@`.
- Название компании → lowercase, обрезаны юридические окончания (ТОО, ИП, LLC и т.п.), пробелы схлопнуты.

### Уровни совпадения

| Уровень | Условие | Действие |
|---|---|---|
| **Сильное (авто-merge)** | точное совпадение телефона, ИЛИ сайта, ИЛИ Instagram/Telegram | автоматически объединяется с существующей записью, новые непустые поля дополняют старые, пустое не перетирает заполненное |
| **Среднее (спросить)** | fuzzy-совпадение названия (rapidfuzz `token_sort_ratio` ≥ 85) при совпадающем городе, ИЛИ совпадение последних 7 цифр телефона при разном формате | бот показывает обе карточки рядом с кнопками «Это тот же лид» / «Это новый лид» / «Объединить, но обновить контакт» |
| **Нет совпадения** | ниже порогов | создаётся новая запись |

### Merge-логика
- Дата создания остаётся от первой записи, `updated_at` и `last_action` обновляются.
- Пустые поля в старой записи заполняются новыми данными.
- Если оба значения непустые и конфликтуют (например, два разных телефона) — новое значение уходит в `comment` как «альтернативный контакт», а пользователю при среднем уровне совпадения явно предлагается выбрать, какое оставить основным.
- Каждое объединение пишется в `audit_log` (action=`merged`) — это и есть основа для `/undo`.

## 9. TELEGRAM UX

### Состояния (aiogram FSM)
`Idle → CollectingLead → ReviewingLead → EditingField / ConfirmingDuplicate → Idle`

- **CollectingLead** — любое сообщение без активной сессии открывает новую; каждое следующее сообщение продлевает таймер на 6–8 секунд. Явное «✅ Готово» или `/done` финализирует сразу, не дожидаясь таймаута.
- **ReviewingLead** — карточка с найденными полями, ⚠️ рядом с полями из `uncertain_fields` и рядом с обязательными, но не найденными (название или хотя бы один контакт).
- **EditingField** — после ✏️ Исправить бот показывает инлайн-кнопки с названиями полей, пользователь выбирает — следующее сообщение целиком идёт в это поле.
- **ConfirmingDuplicate** — только при среднем уровне совпадения дублей.

### Команды

| Команда | Назначение |
|---|---|
| `/start` | приветствие + короткая инструкция |
| `/new` | явно начать новый лид, не сливая с текущим буфером (на случай если два разных лида отправляются подряд без паузы) |
| `/done` | форсировать финализацию текущего буфера без ожидания таймаута |
| `/cancel` | отменить текущий незавершённый сбор |
| `/last` | последние N добавленных лидов (краткий список со ссылками на строки) |
| `/search <запрос>` | поиск по имени/телефону/Instagram/сайту в локальной БД |
| `/stats` | сколько лидов добавлено (всего/за неделю), расход на AI, кол-во дублей |
| `/undo` | откатить последнее действие (создание/merge) |
| `/settings` | город по умолчанию, вкл/выкл уведомления о дублях, ссылка на таблицу |
| `/help` | список команд |

Карточка результата (пример):

```
🏢 Ali Motors
📍 Караганда
📞 +7 700 ...
📸 @alimotors
🔧 Автосервис — ремонт ходовой части
⭐ 5 (3 отзыва)
⚠️ Не найден сайт и email

Добавить в таблицу?
[✅ Добавить]  [✏️ Исправить]  [❌ Отмена]
```

После добавления: «✅ Лид добавлен — строка #127» (со ссылкой на таблицу, если задана в `/settings`).

## 10. ERROR HANDLING

| Ситуация | Поведение |
|---|---|
| LLM недоступен / таймаут | 1 retry с тем же провайдером → fallback на вторую модель через OpenRouter → если всё упало, бот показывает исходный текст и предлагает быстрый ручной ввод (по одному ключевому полю за раз) |
| LLM вернул невалидный JSON | 1 retry с указанием ошибки валидации в промпте → при повторной неудаче — ручной ввод как выше |
| Google Sheets API ошибка (429/5xx) | лид уже сохранён в SQLite — запись в Sheets ставится в очередь ретраев с backoff; пользователь видит «✅ Добавлено в базу, синхронизация с таблицей чуть задержится» |
| Мусорный/нерелевантный текст (AI вернул почти все поля null) | бот не создаёт пустой лид, а прямо пишет «Не удалось распознать компанию — пришли больше деталей» |
| Нет ни названия, ни контакта | карточка не даёт нажать ✅ Добавить, пока не заполнено хотя бы одно из двух |
| Сомнительный дубль | см. раздел 8 — явный выбор пользователя, ничего не объединяется молча |
| Сетевые сбои Telegram API | стандартный retry-мидлварь aiogram + разумный backoff |

## 11. SECURITY & LOGGING

**Доступ.** Бот приватный — мидлварь проверяет `telegram_user_id` по allowlist из таблицы `users` (или простого списка `ALLOWED_USER_IDS` в env для MVP). Неизвестным пользователям — один нейтральный ответ («бот приватный») и тишина дальше, без утечки деталей.

**Секреты.** `BOT_TOKEN`, `OPENROUTER_API_KEY`, `GOOGLE_SERVICE_ACCOUNT_JSON` (base64), `GOOGLE_SHEET_ID`, `ALLOWED_USER_IDS` — только через переменные окружения Railway, ничего в репозитории, `.env` в `.gitignore`. Сервис-аккаунту Google выдаётся доступ только к нужной таблице, не ко всему Drive.

**Инъекции в таблицу.** Любое значение, начинающееся с `=`, `+`, `-`, `@`, перед записью в Google Sheets экранируется ведущим апострофом — защита от formula injection, поскольку часть данных — это copy-paste из внешних источников.

**Логирование.** Структурированные JSON-логи с `session_id` для сквозной трассировки одного лида: входящие сообщения → вызов LLM (модель, токены, латентность, стоимость) → решение дедупликации (score, с кем сравнивали) → результат записи в Sheets → действия пользователя (confirm/edit/undo). Полные тела ответов LLM хранить на уровне DEBUG и не бессрочно — старше 30 дней можно ротацией удалять, `raw_messages` (исходный текст лида) хранится бессрочно как источник истины для пересчёта.

   EditingField, ConfirmingDuplicate)

  "address": "string | null",
  "phone_raw": "string | null",
  "phone_e164": "string | null",
  "has_whatsapp": "boolean | null",

Жёсткое правило для системного промпта: модель НИКОГДА не придумывает отсутствующие

Требуй строго валидный JSON без markdown-обёртки, парси через Pydantic-модель.

ДЕДУПЛИКАЦИЯ
Нормализация перед сравнением: телефон → E.164 + сравнение по последним 9-10 цифрам;
сайт → без протокола/www/query-параметров/trailing slash; instagram/telegram → lowercase
без @; название → lowercase, без юридических окончаний (ТОО/ИП/LLC), схлопнутые пробелы.

Уровень "сильное совпадение" (авто-merge, без вопросов пользователю):
точное совпадение телефона ИЛИ сайта ИЛИ instagram/telegram.

Уровень "среднее совпадение" (спросить пользователя явными кнопками):
rapidfuzz token_sort_ratio по названию >= 85 при совпадающем городе,
ИЛИ совпадение последних 7 цифр телефона при разном форматировании.

Merge: дата создания — от первой записи; пустые поля старой записи дополняются новыми
данными; при конфликте непустых значений — новое уходит в comment как альтернативный
контакт, пользователю на среднем уровне совпадения дать явный выбор. Каждый merge — запись
в audit_log (для /undo).
